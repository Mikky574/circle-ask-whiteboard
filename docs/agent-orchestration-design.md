# 面向功能验收的多代理工作台

状态：2026-11-24 产品与工程设计，基于 `8d295f0` 核对现状。本文定义下一阶段的目标，不表示调度器已在正式服务上线。验收清单见 [orchestration-acceptance.json](orchestration-acceptance.json)，其中所有新增用例均为 `pending`。

## 1. 定位：让功能从意图走到可核对的交付

用户在项目的不同功能节点上下达指令，系统理解意图、确定验收、拆分与调度任务、协调交付，并用真实验证说明功能完成到什么程度。白板是这个过程的操作界面。子代理持有一项功能的上下文并协调工作，不等于每张卡片常驻一个模型。

用户首先关心：**想要什么行为、现在缺什么、谁在做、等什么、结果能不能用、哪里需要我决定。** 文件、函数、聊天记录、实验图表都是回答这些问题的依据。

功能图按用户可观察的能力组织，例如「从图片得到识别结果 → 不确定时拒识 → 收集待复核样本」，而不是先按前端、后端、数据库或文件名拆树。内部实现可以跨多个功能，能力分析必须标明源码、测试或用户说明依据。缺证据时保留未知，不凭模型判断宣布项目已被理解。

| 一级能力 | 用户操作 | 应得到的结果 |
| --- | --- | --- |
| 找准要改的功能 | 在任意节点描述想法，或组合几个节点发令 | 关联的已有能力、目标、差距、约束和待澄清事项 |
| 确定完成条件 | 查看、修改验收场景 | 可观察的行为、可运行测试或明确的人工验收、固定的版本 |
| 在多个节点推进工作 | 分别发送实施、研究、验证或纠偏指令 | 独立任务、依赖、运行者、等待原因及可追踪的交接 |
| 核对并集成交付 | 看结果、处理真正的冲突与人工验收 | 与当前验收匹配的交付件、集成验证证据、未解决事项 |

继续保留子白板下钻、实验对比、图片和知识资料。它们是功能节点下的阅读与证据入口；不再用增加说明卡的数量来代表任务进展。

## 2. 一条完整使用路径

1. **用户在功能节点发指令。** 例如「这里增加不确定结果的复核流程，同时把结果导出补齐」。发送时固定选中范围、原始指令和指令编号。系统区分解释、规划、实施、验证和控制运行；推断置信度低或目标有实质歧义时提问。
2. **只读核对现状。** 阅读入口、流程、相关测试和约束，产出带依据的能力假设：已核实、推断待核对、目标、缺口、未知。事实、目标和实现状态不能混为一色的完成标签。
3. **提出局部计划。** 展示新增／修改的功能、验收、任务与依赖，以及为什么影响这些节点。保留原有节点身份、用户文字与正在运行的任务；不重建整张板。单纯讨论不触发改码，明确实施指令在其授权范围内自动进入执行。
4. **先确定怎样验收。** 固定场景、测试、输入数据、环境与预期结果。新增功能或修复先验证有效 Red，再实施与验证 Green；任务拆分围绕交付及验证依赖进行。
5. **从多个节点同时发令。** 可以一边实现复核流程，一边完成导出。系统统一检查权限、依赖、资源与并发额度；提交成功不代表已经开始运行，排队时直接说明原因。
6. **按交付件协作。** 某任务需要接口、数据或另一个任务的结果时，向对应任务发送定向请求。对方提供有版本的交付件，消费者验证并接受后，依赖才解除。
7. **核对集成结果。** 验证器在集成版本上运行当前验收与回归。模型回复「完成」不推进功能完成状态。冲突、人工验收与授权范围外的动作进入统一待决队列；用户在原节点或队列中回答即可继续。

授权随作用范围与任务保留，不要求用户对冻结测试、普通测试运行和每个无冲突子步骤重复确认。执行授权记录项目／路径、动作与命令范围、可接收代码的后端、预算、有效范围／期限和发布目标，并可撤销。发令处简明展示沿用的已有授权；已有项目约定继续有效。扩展范围、不可兼容的约束、用户保留的决策关口仍需明确决定。

## 3. 白板结构由同一张带类型的图投影

### 稳定的功能结构与变化的执行现场

功能、需求、验收和任务都有稳定 ID 与各自版本。结构归属、执行依赖和追溯关系使用明确的边类型；不能继续借 `parentId` 同时表示所有关系。

| 对象 | 必须说明什么 | 不应混入什么 |
| --- | --- | --- |
| 功能／需求 | 谁使用、输入、可观察输出、边界、现状与目标 | 某一次运行的进度 |
| 验收场景 | Given／When／Then、验证方式、版本、所需证据 | 模型口头判断的通过 |
| 工作任务 | 要交付什么、输入输出契约、满足哪些验收、预期读写与资源范围 | 固定绑定某个常驻模型 |
| 指令 | 谁在何范围要求做什么、授权、幂等编号 | 由日志反推的用户意图 |
| 运行尝试 | 谁在什么输入版本和工作区执行、状态、阶段、预算、租约 | 卡片的固定归属关系 |
| 交付件／验证记录 | 不可变内容、版本与摘要、产生者、输入依据、真实测试结果 | 无版本的「最新文件」 |
| 消息／冲突／决定 | 具体对象、请求回复、受影响版本、需要谁做何决定 | 无目的的全员聊天流 |

关系分开：

- `contains`：阅读归属，禁止成环。
- `requires`：执行前置依赖，禁止成环；消费者需要哪个交付件契约必须写清。
- `satisfies`／`verifies`：任务满足哪些验收，验收检查哪些需求，允许多对多。
- `produces`／`consumes`：具体运行产生／消费哪一版交付件。
- `constrains`／`references`：约束及参考依据，不自行触发执行。

归属和依赖存在同一个版本化图中，是不同语义的边；界面树、执行图都是它的投影。移动卡片、调整阅读顺序不会改执行依赖，增加依赖也不会把卡片偷偷移到另一个父节点。

**不要求每条需求严格嵌成「功能 → 需求 → 测试 → 任务」的唯一树。** 一个任务可以影响多个功能；一个场景可以需要几个任务。验收覆盖与交付依赖通过带类型的边追踪。

### 意图变化怎样更新图

解析输出 `PlanChange`：基准图版本、源指令、受影响节点与边的基准版本、待新增／修改的字段和边、依据、假设、影响范围。先校验作用范围、引用、环与涉及实体的版本，再原子应用。图级快照用于追溯，不能因无关分支改变就让所有任务失效；也不得覆盖用户在其他分支的新工作。

对已授权且含义明确的指令可直接应用局部计划并报告差异；有歧义、改变确认约束或扩大执行范围的部分进入待决。计划本身可以修订，但已派发运行继续绑定旧的输入快照。新验收生效后，旧结果可以被阅读，不能被当成满足新版本的证据。

## 4. TDD 约束的是证据与推进顺序

| 工作性质 | 执行契约 |
| --- | --- |
| 新增行为／修复缺陷 | 先复现预期的行为缺口并记录有效 Red，再实施、Green、集成回归 |
| 已有能力核对 | 可以直接取得验证证据，不为了流程制造失败 |
| 保持行为的重构 | 固定现有通过基线，重构后对比相同行为与回归 |
| 实验／训练优化 | 预先固定数据名单、基线、指标方向、阈值与约束，再运行比较；结论保留适用范围 |
| 不能自动化的体验验收 | 明确人工判断条件和所需截图／录屏／说明，保持待人工验证 |

Red 检查预期失败理由与实际失败是否对应，不仅检查非零退出码或异常类。环境缺依赖、非预期导入错误、错误测试路径、零条测试或环境启动失败属于无效运行；不能靠这些解锁实施。新增接口本身尚不存在时，可以先用接口骨架取得行为断言失败，或在运行前固定预期的缺失符号签名并确认其确为功能缺口，不能笼统地把所有导入失败视作有效或无效。

测试冻结包括实际测试及 fixture、验证配置等依赖清单和摘要。实现运行不能通过删除场景、跳过测试或放宽阈值获得 Green。确需变更测试时修订验收版本，重新判定受影响的基线与证据；保留变更理由。测试评审与验证采用独立职责，不要求每项职责常驻一个额外 agent。

验证记录至少绑定：验收版本、测试包摘要、被测源码 commit、输入数据版本、环境／运行器标识、命令、退出码、实际用例和结果、原始证据引用。关键验收用正反样例或有针对性的反证探针确认测试能区分目标行为；缺少这类依据时标出证据局限。发现 Red／Green 不一致或已知不稳定用例时，按预先配置的有限复核策略检查，保持不稳定状态，不能挑一次通过当成稳定证据。

worker 分支通过与集成版本通过分开展示。只有当前集成版本的有效证据及必需人工验收齐备，功能才显示已满足。

实验比较图与说明图片继续直接展示，但必须指向对应数据和运行。模拟、诊断替代、真实训练结果与实际部署验证分开；不能将真值替代的诊断收益当成模型已取得的改善。

## 5. 多点命令、子代理与中央调度

### 职责

- **功能子代理**理解本功能的上下文，提出计划、跟踪子任务与汇总进展。它不能自行扩大权限或绕过调度器启动任意工作。
- **工作 agent**领取一个有范围、输入快照、交付契约与预算的运行尝试。
- **协调器**统一接收指令、持久排队、检查依赖、分配资源、投递消息及处理状态变化。何时能启动由确定规则决定，模型负责提出计划与解释。
- **验证器**运行测试、核对版本与交付资格。**集成队列**串行构建候选集成版本并重测；agent 可提出冲突修复方案，不能仅凭一句「已解决」获得集成资格。

角色和供应商解耦。一个 CLI 会话不自动等于一个任务，也不等于 Codex 桌面侧栏的一条聊天。会话可从图、已接受交付和事件重建，不保留只有会话知道的任务状态。更换 agent 或重试时保留任务身份，创建新的运行尝试。首个并发闭环至少需要两个真实隔离的代码运行，不能把四个并行问答称为已经完成调度系统。

### 调度资格

任务输入版本有效、必要的上游交付已被接受、授权覆盖所需动作、后端实际可用、资源与并发有额度时，才可领取。选用模型不等于已经验证登录或工具能力。

同一任务可以有不同尝试，但一个执行槽只有一个有效租约持有者。任务声明的读写范围只是预检信息；不同文件也可能共享接口、数据库、测试端口、GPU 或数据集。不能凭卡片位置或路径不重叠宣布无冲突。

不同指令 ID 还可能对同一验收重复要求实施。这属于范围重叠，不能靠请求去重解决：默认关联并跟进已有活动任务；出现不同目标或相互矛盾的命令时展示合并／替代／独立实验的选择。只有明确指定独立尝试且资源与集成策略允许时，才并行启动同一验收的竞争实现。

### 工作区与集成

首版实际执行限于用户选定的 Git 项目；非 Git 目录继续只读分析，写入能力另行设计。每个代码运行基于明确 commit 创建独立 worktree。保护用户原目录的已有修改，输出 patch／commit 和证据，不让多个 agent 共用一个可变目录。

测试进程也有单独的临时目录、数据库、端口与可变缓存；不能因源码目录隔离就假设运行时已隔离。worktree 共享的 Git 元数据操作需要受控串行，GPU 等无法复制的资源显式租用。

worktree 用于隔离改动，不是通用 shell 的安全沙箱。执行范围需要由工具接口和工作区策略实际落实；不能仅在提示词里写「不要改其他文件」就声称已有隔离保证。

集成按租约串行执行：核对输入与验收版本 → 合并到候选集成工作区 → 运行必要验收与回归 → 记录交付决定 → 发布新的集成头。无文本冲突也不能跳过行为回归。接口或语义冲突保留双方版本与失败证据，可请求协作修复；不能达成兼容决定时交给人。

无明确发布授权时产物止于内部集成分支；发布到用户分支或外部目标按项目已有约定与本次授权执行。已有主分支提交约定不被重置为每步审批。发布前核对目标分支与工作区状态，不能覆盖用户主副本的未提交修改。

## 6. 交流围绕可接受的交付件

消息正文用自然语言，外层包含稳定的 `messageId`、`kind`、发送／接收任务或运行、节点范围、`requestId`／`replyTo`、输入版本、交付件 ID 与是否需要人决定。类型覆盖提问、回答、交接、阻塞、冲突与决定。

消息持久投递、按 ID 去重；定义回复期限、拒绝、接收者失败和无法解决时的上报。收到消息不代表接受交付。只有消费者或验证器在当前契约下产生 `artifact.accepted`，对应交付依赖才满足。agent 之间的答复不能授予原本没有的项目权限。

`needsHuman` 是模型可提出的建议，是否进入待决及能否继续由协调器结合授权、契约和验收规则判定。涉及授权、破坏兼容或验收定义的提问超时默认阻塞；只有预先授权的低影响假设可记录后继续，不能让所有超时自动变成默认同意。

每个交接有请求、提供、消费验证、接受／拒绝四步。冲突项记录受影响契约、各方产物、失败证据、候选修复和最终决定。协作后仍需真实的兼容测试及集成验证。

**示例，非已执行结果：** A 实现低置信度拒识，B 实现待复核样本收集。A 用 `labelId=null` 表达未知，B 却把每条结果都按已有类别处理。系统从交付契约或集成失败定位不一致，在两节点之间产生冲突项。双方商定版本化结果契约，补上「未知结果进入复核队列且不伪造类别」的验收；受影响任务按新契约重做与验证。仅双方回复「同意」不能关闭冲突，消费者验证与集成验收都通过后才关闭。

人的待决队列合并重复问题，按阻塞范围和影响排序。一般状态报告留在节点活动里；真正需要选择、补充输入或进行人工验收的项目才进入队列。

## 7. 界面围绕工作组织

```text
项目 / 功能路径          当前意图与范围        正在运行 · 等待 · 待决
┌────────────────┬──────────────────────────────┬──────────────────────┐
│ 功能树          │ 当前功能及子功能／验收投影       │ 选中节点              │
│ 已有 / 目标     │                              │ 当前目标与指令         │
│ 缺口 / 未知     │ 能力卡显示：目标、验收覆盖、       │ 验收与依据             │
│                │ 正在做什么、阻塞、最近交付        │ 运行与交付             │
│ 搜索 / 关注     │                              │ 定向协作 / 待决        │
└────────────────┴──────────────────────────────┴──────────────────────┘
当前工作：任务 A 实施中 | 任务 B 等待接口 v2 | 一项冲突待处理
```

- 默认看功能，点击进入以它为根的子白板。根节点固定，展示当前目标、已有／目标差距、验收与可执行工作；不自动把所有日志展开成子卡。
- 切换「功能」「验收」「执行依赖」时复用相同实体。知识资料、原始问答与实验证据在相关节点阅读，不与调度状态争抢主界面。
- 节点命令框显示明确作用范围及执行含义：只分析、形成计划、实施当前验收、验证、纠偏。选多卡时显示共同范围。发送后立即出现持久指令回执与运行入口，不依赖用户留在当前页。
- 同时工作条显示运行／排队／阻塞及原因，点击回到对应节点。节点详情按「目标 → 最近动作 → 实际证据 → 下一步／待决」解释发生了什么。
- 展示观察到的工具行为、关键决策依据与交接，不声称展示未暴露的模型内部思维。低层日志可展开，默认不占满功能图。

## 8. 持久化、版本与故障边界

### 一个事实源，不让进度刷坏白板

建议复用同一份本机 SQLite，在新表中存放版本化功能图、指令、任务与运行、租约、交付、验证和消息事件。高频进度不重写 `organization` 整板 JSON，也不提升旧白板的内容 revision。

新功能图是调度实体的事实源，旧卡只通过稳定映射作为参考与证据；不要同时在整板 JSON 和新表各维护一份可编辑的调度图。计划改变与相关失效标记在数据库事务中完成。旧白板存储与版本入口继续承担原内容的保存。

| 边界情况 | 必须执行的约定 |
| --- | --- |
| 重复发送／网络重试 | 客户端 `commandId` 在重试中保持不变；服务返回同一指令与运行。同 ID 不同负载报冲突。用户明确再次运行用新 ID，不能被文本哈希误去重。 |
| 需求变更 | 运行绑定输入快照。新验收生效后，旧结果标为过期；能否复用必须重新验证，不能直接打完成勾。 |
| 集成头前进 | 交付在自己的基线仍可有效，集成资格变为待核对；在新集成头重放／合并并验证，不能把一切基线不相等都当成内容已失效。 |
| 暂停／纠偏 | 区分等待协作、请求暂停与实际已停止。后端没有检查点能力时，停止进程并保留工作区，恢复创建新尝试；不能显示成原进程已可靠挂起。 |
| 取消与结果竞态 | 持久取消决定与交付提交有线性化边界。取消先成立则迟到结果不被接受；提交已成立则明确返回已交付，不能假报已取消。 |
| 崩溃／租约过期 | 先恢复核查，保留工作区与记录。epoch 阻止旧持有者提交；租约过期不证明旧进程已退出。无法确认释放的端口／GPU 等资源保持隔离待处理。 |
| 重启后恢复 | 写任务不盲目重放；核对存活进程、已落盘产物、输入版本和集成决定，再继续或建立新尝试。不承诺任意外部副作用恰好执行一次。 |
| 多端口／多进程 | 在 SQLite 事务中统一领取租约、执行并发额度和集成资格；进程内字典仅缓存。旧执行路径也必须登记或互斥，不能留下可绕过的旧入口。 |
| 事件重连／重复交付 | 事件有稳定 ID 与递增游标，可重放、去重、重建视图；消息写入与待投递记录原子提交，不能凭浏览器内存维持协作。 |
| 删除／整理／恢复 | 运行中的节点保持身份；归档不抹去任务证据。旧白板整板恢复不能静默撤销或复活调度运行。迁移期间两个恢复语义分开展示。 |

运行状态与工作阶段分开：状态说明排队、执行、等待交付、等待人、停止中、恢复核查、成功、失败或取消；阶段说明分析、设计测试、Red、实施、Green、重构或集成。任务成功表示符合任务交付契约，功能满足仍须当前集成验收。

## 10. 先用真实闭环证明方向

| 里程碑 | 范围及必须展示的结果 | 出口 |

## 11. Claude 讨论后的取舍

本轮应用户要求，通过已安装的 Claude CLI 进行两轮产品架构讨论。只提供通用需求与已核对的源码事实，禁用工具；完整提示和回答留在本机讨论目录，不提交会话原始数据。

第一轮重点采纳：验收契约优先于增加并发数；能力解析应保留未知；运行不能靠整板 JSON 高频保存；冻结测试与实际执行证据要分开；跨端口的进程内锁不能解决全局调度。

第一轮提出「一期写任务并发为一」「每阶段固定人工确认」。本设计将单任务闭环作为内部里程碑，正式多代理首版仍要求两个隔离代码运行；用户已有授权覆盖的步骤自动推进，人处理歧义、冲突、人工验收与保留的关口。

还修正了两项容易误实现的细节：去重使用稳定指令 ID 而不是指令文本哈希，保留用户明确重跑的能力；租约失效不等于旧进程退出，过期持有者必须被禁止提交，无法确认释放的独占资源不能立即复用。

第二轮采纳：显式执行授权、运行环境隔离、实体版本绑定、不同指令的范围重叠检查、可重建会话、预声明的缺失符号 Red 和不稳定测试处理。保留两处判断：已明确实施指令及验收无需强制再点一次批准；Windows 取消能否终止整棵进程树应实际验证，确认失败的运行进入隔离待核查，而不是声称已可靠停止。
