# 从使用结果提炼项目功能

当前建设重点是：读者先看懂项目解决什么问题、有哪些不同的用途，再沿真实使用场景找到实现与证据。调度设计建立在这张可理解的功能地图上，另见 [后续多代理设计](agent-orchestration-design.md)。

## 阅读层级

| 阅读范围 | 应回答的问题 | 合适的内容 |
| --- | --- | --- |
| 项目总览 | 谁用、用来完成什么、责任到哪里为止 | 项目目的、主要结果与范围 |
| 功能 | 用户能完成哪件独立的事 | 使用者、输入、可观察结果、边界、核对方式 |
| 使用场景 | 何时触发、如何操作、结果如何出现 | 一条实际流程、成功条件、重要失败／边界情况 |
| 行为或判断 | 流程在哪一步产生结果或发生分岔 | 可观察的动作、触发条件、失败与恢复 |
| 实现依据 | 这些行为怎么得到证明、从哪里改 | 源码与调用、参数、测试、文档与实验记录 |

证据充分的分支可以按这五级展开。原生初始化允许第六级补充特定证据的细节。简单功能可以保持很浅。较复杂功能按不同用户目标组织，避免「整个功能」「通用技术层」「某个参数」成为同级。

例如，功能层可以是「不确定时保留待复核结果」，场景层是「低置信输入进入复核列表」，实现依据再放阈值处理、输出结构与相关测试。领域术语可以保留；把类名翻译成中文仍不足以说明功能。

## 自动解析的顺序

1. 读取项目说明、入口与有代表性的实现，沿输入到输出追一条真实使用路径，查找相关测试或验证说明。
2. 从可观察结果反推使用场景，再将服务同一用户目标的场景归到功能下。目录结构用于找证据，不直接决定功能结构。
3. 写总览与独立功能。外层卡必须能脱离子卡读懂；按内容决定数量，简单项目可只有「总览＋一项功能」。
4. 自查外层是否混入内部函数、某个参数或泛化技术章节。仅对有独立内容的场景继续展开；可用卡号是上限，不是生成配额。
5. 校验卡号、关系、记录与文件范围，再交给前端。文件存在说明可以定位依据，不证明模型已读懂其全部内容，更不证明测试已经运行。

目前每次初始化仍是同一次模型会话内的阅读、综合与自查，并没有独立的语义评审模型。结构校验能拦截缺少功能说明、虚构文件引用、越界路径和无效关系，不能自动证明标题与功能分组最优。真实仓库试读与人的修订仍是质量评估的一部分。

## 功能记录与依据分开

原生「初始化工程介绍」的总览与一级功能要求 `capability`，深层可为 `null`。绑定仓库的普通整理也可以返回这份记录；用户提出按功能整理时，使用场景与可见结果优先。模型候选中的文件引用放在 `repositoryFiles`，不再要求每张卡正文包含反引号文件名。

```json
{
  "capability": {
    "version": 1,
    "audience": "需要核对识别结果的使用者",
    "input": "待识别图片",
    "outcome": "得到候选结果或待复核提示",
    "boundary": "不自动确认不确定类别",
    "verification": "核对已知和低置信输入的可见结果；此处尚未验证"
  },
  "repositoryFiles": ["src/predict.py"]
}
```

以上是格式示例，不代表该文件或功能属于某个实际项目。五项说明各最多 200 字。文件必须能在绑定仓库的受限读取范围内定位；符号引用可以写 `src/predict.py#predict`，保存时规范为文件路径，符号本身是否存在不由这一文件检查保证。

功能说明随卡片保存和便携导入导出。画布上只改标题会保留功能说明；改写正文时以新正文为准。外部服务技能也支持写入这份记录。

## 呈现方式

项目默认打开可编辑画布。拖卡头移动卡片，双击标题或点「编辑」打开改写表单。点「进入分支」只查看这张卡和它的下级，点路径可返回上级或整板。可以在分支内手写子卡，也可以点卡片上的「拆分」生成候选并勾选要加入的内容。既有连线操作可调整归属。

拆分可按项目功能、使用场景或实现与验证展开。自动选项结合当前卡的层级与提问方向。项目功能要有可识别的入口、输入和能重复使用的结果。使用方式相同的多次具体操作归到同一功能下。生成时参考现有子卡与邻近主题。资料不足以提出独立子卡时，系统可以给出空结果。通过校验的功能候选会保留完整的功能说明，选择加入后可在功能目录下钻。

在项目画布的圈选模式，从空白处画圈或斜拉即可选整卡。圈中预览会随手势更新，容忍少量漏边。拖动任一整选卡的卡面可移动整个选区。Shift 点选增减卡片，Alt 拖动圈文字，按住空格拖动画布。圈选算法用卡片中心和覆盖情况判断命中，缩放后仍按实际卡片范围计算。

「阅读资料」从同一分支打开功能目录、场景、源码与实验依据。「编辑画布」回到这一支。功能与场景都可打开对应卡片的提问框。实验指标、图片、资料和画布沿用同一批卡号与保存内容。

「流程与分组」把下级主题和各自的说明聚在一起。确认某个场景有明确顺序后，可用「设置流程」选出 2 至 12 张直属卡并排序。桌面横向显示主步骤与箭头，窄屏纵向排列，每一步的子卡紧凑地放在下方，可以继续点入。`flowSteps` 随父卡保存，是有顺序的子卡编号列表。流程中任何一步离开当前分支时会恢复为主题分组，重新设置后再显示箭头。

有已核对的职责与依赖关系时，可以用「项目结构」阅读。宽屏显示分区、带文字的主路径、旁路和回写。窄屏按职责区浏览，展开「全部关系」核对方向和依据。点图中节点可查看并进入原卡，点连线文字可读对应证据卡。初始五至六级层次仍用原卡片关系表达。

有结构图的白板在同一条工作区导航里切换「项目结构」和「项目画布」。结构图上选中的卡可直接打开右侧编辑栏，保存回同一张卡。切到画布会展开并定位这张卡。画布选中更深的细节时，返回结构图会标出最近的对应节点，并保留该细节卡的正文。移动卡片、框选和改连线仍在画布操作。

在结构图节点上右键、点「⋯」或按 `Shift+F10`，可直接编辑原卡、进入以它为根的可编辑分支、在当前画布定位或查看卡片。菜单定位在节点附近。画布的卡片右键菜单也可进入该分支。

## 工作区的状态归属

| 状态 | 负责位置 | 包含的内容 |
| --- | --- | --- |
| 项目入口与归属 | `app.js` 与 `board_sync.js` 的入口 | 项目登记、白板编号、外层页面、资料归属 |
| 白板文档 | `organization.js`、`memory.js` 与 `board_sync.js` | 卡片、父子、关系、手工坐标、折叠与白板版本 |
| 查看状态 | `workspace_navigation.js` 与 `workspace_controller.js` | 当前模式、画布分支、阅读根、当前卡片、返回分支。由工作区统一写入 URL |
| 当前工具操作 | 画布、导图、阅读和编辑器的组件 | 相机、手势、连线工具、提问和卡片编辑草稿 |

导航以真实卡号在各视图间交接。要跳转的卡超出当前分支时，使用能包含它的最近祖先分支。旧卡号链接、浏览器前进后退、折叠状态和手工排布继续沿用原有入口与文档。导图的本地偏好用于无显式模式的旧入口，打开有模式的链接时使用链接指定的视图。

在便携白板文件的 `organization.current.projectStructure` 记录图的表达方式。`version` 为 `1`，`rootId` 指定在哪张卡显示结构图。`zones` 中每区有 `id`、`title`、`role`、`size`、`lane` 和 `nodes`，节点用 `cardId` 引用现有卡。`links` 使用节点的 `id` 作 `from` 和 `to`，提供关系 `label`、类型 `kind` 与可选的证据卡 `evidence`。只有核对过源码或实际用例的关系才录入。删除卡片后图会隐藏失效引用，活跃白板中的其它卡片仍可正常编辑。

本轮不自动重排或重写已有项目白板。旧内容需要针对真实项目重新核对后逐支修订，不能因更新了生成规则就假定已有卡片已经转换为功能地图。

## 验证范围

- `test_capability_intro.py` 核对无填充卡的小项目、外层功能契约、独立文件依据与禁止在外层自动插入源码卡。
- `test_capability_data.js` 核对功能说明与文件依据经过清理、导出和导入仍保持。
- `test_repository_binding.py` 保留源码范围、层级与深层源码预览回归。
- 本轮对本项目实际调用了本机 Claude CLI 做只读试读；首次输出中的分类错误与不存在的文件被拒绝，修正后通过相同服务校验。单仓库试读不代表跨项目抽象质量已经得到全面验证，试读产物保留本机。

## 下一轮验证

选一个有明确入口的应用和一个以脚本驱动的研究项目。先只看一级标题和结果，检查能否概括项目用途并找到目标功能。再从一个场景核对入口、可见结果、失败边界和源码依据。记录误分组与过度技术化的实例。

如果同类偏差反复出现，将功能分组审阅拆成独立步骤。评审只看功能与场景的归属、证据和待核实项，返回可核对的局部修订；通过同一结构校验后再应用。调度工作继续以功能地图和核对方式为输入。
