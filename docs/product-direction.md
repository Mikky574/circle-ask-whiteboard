# 项目定位与主要工作流程

本项目的目标是面向功能验收的多代理工作台：用户在不同功能节点描述意图或下达指令，系统据此核对现状、确定验收、拆分与调度任务、协调版本化交付，并解释结果及待决事项。白板是工作界面，卡片、导图和实验资料用于表达功能、约束、执行关系与证据。

2026-11-24 的 [功能验收与多代理调度设计](agent-orchestration-design.md) 定义下一阶段结构、TDD 契约、并发协作和里程碑；[验收清单](orchestration-acceptance.json) 的新增用例均未实现或运行。该设计经本机 Claude CLI 两轮讨论后整理，不代表正式白板已具备任务调度器。

## 用户如何工作

1. **进入一个真实项目。** 白板绑定项目目录，先掌握项目目标、使用流程、主要模块和边界。
2. **逐层理解。** 从一个模块继续问到实现方法、数据流、文件和函数调用、异常分支及测试。说明应引用源码、文档或运行证据；缺少证据时说明尚待核实。卡片、子卡和附件共同承载细节。
3. **手动搭建想法。** 用户可以直接新建、编辑和摆放卡片，记录需求、限制、方案、疑问或验收条件。创建卡片无需先发起一次模型问答。
4. **组合研究范围。** 用户多选或关联已有模块与手写卡片，表达“结合这些内容分析或修改”的意图。AI 应读取明确选中的内容，并区分需求、已有实现、约束和参考材料。
5. **形成并执行需求。** 目标流程按用户本次指令确定修改对象、范围、验收与任务依赖，由适配的 agent 在隔离工程工作区执行。新增行为先确认有效 Red，再实施、验证与集成；已有能力核对和重构不人为制造失败。此项目级执行闭环尚待建设。
6. **多点推进并核对交付。** 目标流程支持在不同节点发令、持久排队和并行工作；合作围绕指定版本交付件进行，冲突留下证据与决定。功能满足由当前集成版本的有效验收决定，模型回复完成不能代替验证。当前可保存说明、实验与外部会话交付结果，尚不能自动完成以上调度。

## 卡片与关系的含义

卡片可以是用户写下的需求或事实，也可以是 AI 生成的说明、方案或任务。用户手写内容应作为本次上下文的明确输入。图钉表示重要，不代表已确认或已实现；模型提出的方案也不能仅因生成成功就视为已经落地。

目标图需要区分几类关系：

- **结构归属**：哪个模块属于哪个模块，负责逐级展开、收起、路径和下级计数。
- **执行依赖**：工作何时可以开始、需要哪个版本的交付件；这类关系禁止形成环。
- **验收追溯**：任务满足哪些场景、场景核对哪些需求，可以多对多。
- **研究关联与约束**：共同考虑的资料与限制。建立关联应保留原有模块的结构归属，不自行触发执行。

这些关系属于同一个版本化图，阅读树与执行图是不同投影。现有手工连线仍主要表达结构归属；新的类型化关系尚未落地。

当前用户明确多选的卡片优先于隐式草稿隔离。选择两张独立草稿，或混选正式模块和草稿，不应仅传递卡号与短摘录而过滤其正文。未选中的其他草稿继续保持隔离。一次上下文仍受现有数量与长度预算限制，不能承诺将整张大板全部送给模型。

例如手写「新增离线能力」需求卡，同时选中「现有处理流程」「设备资源限制」「验收条件」，向 AI 发出“结合这些内容细化方案”的指令。结果应能对应到这几张输入卡；执行后再更新实现和验收依据。

## 当前能力与缺口

| 能力 | 当前实际情况 |
| --- | --- |
| 手动创建、编辑、摆放、多选卡片 | 已有；新卡可作为独立草稿，再整合到主结构。 |
| 明确选择的多张卡共同提问 | 已有上下文组装；修正了混选或多个独立草稿时正文被隔离规则过滤的问题。当前详细上下文最多取 8 张选中卡，并有字节预算。 |
| 手动连线 | 主要表达父子归属。整理后的结构每卡一个主要父节点，新连线会替换父节点。带类型、可跨多个模块的研究关联仍待实现。连上不等于普通问答必定遍历全部相邻卡片。 |
| 深入读取项目 | Codex/ZCode 可按需读取绑定目录；列表和文件读取有范围与大小限制，可继续定位下级目录。并非预先完整索引并理解了每个工程。 |
| 从需求修改绑定的任意项目 | 尚未闭环。绑定目录当前只读，已有改码路径针对白板原型的前端白名单。项目工作区写入、测试执行和结果回写需要单独落实。 |
| 需求和验收组织 | 有目标、约束、决定、任务依赖与验收字段；需求/测试用途目前主要在功能样板开放，尚未统一为所有项目的工作流程。 |
| 保存、版本与交接 | 已有服务共享保存、历史、Fork、便携导入导出；这些能力支撑项目工作连续性，不能代替源码和真实测试证据。 |
| 多点指令与持久调度 | 已有并行问答与进程内限额，尚无持久任务队列、跨端口租约、重启恢复和任务交付依赖。 |
| 多 agent 协作与集成 | 尚无绑定项目的隔离并发工作区、结构化交接、冲突闭环和串行集成验证；并行问答不等于并行实施。 |
| TDD 与功能完成判定 | 尚无冻结验收、有效 Red 检查及集成版本证据绑定；现有任务验收文字与样板通过标签不能替代此契约。 |

后续实现围绕上述主要工作流程核对：用户能否表达意图，AI 是否实际获得相关输入，是否对正确工程执行，以及结果是否有可核对的证据和明确归属。先跑通单任务的真实 TDD，再以两个隔离代码任务、一次交付协作／冲突和集成验证证明并发闭环。未达到该出口时不将现有正式白板标为已完成多代理调度。

实现入口：上下文和手工卡片见 `app.js`，关系与结构见 `organization.js`，执行范围见 `server.py`、`backends.py` 和 `zcode_workspace.py`。现有机制见 [当前架构](current-architecture.md)，操作见 [功能说明](whiteboard-feature-guide.md)。

多卡上下文回归运行 `node test_multicard_context_browser.mjs`。用例通过实际界面手写卡片并多选，核对意图分类与正式问答两次请求里的完整正文，同时检查未选草稿隔离和单草稿下级。`MULTICARD_BASELINE=1` 仅恢复旧范围判断，可复现明确选中卡片丢失的问题。测试使用隔离浏览器和模拟模型，不表示已验证真实项目改码。
