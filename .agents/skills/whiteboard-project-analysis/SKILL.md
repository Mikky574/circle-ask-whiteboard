# 圈问白板：从使用需求读懂代码仓

## 从一个实际场景出发

- 先弄清使用者要完成什么、输入和输出是什么、什么情况算失败。接手项目的读者还需要知道从哪里开始读、变更在哪一层、哪些约束不能破坏、如何得到可复现的验收结果。
- 在项目授权的目录内找 README、仓库说明和构建清单，再跟一条真实调用路径：用户动作 → 入口 → 核心方法与配置 → 返回值、错误或回退 → 可核对的测试。只读与问题相关的源码、配置和测试，跳过凭据、生成物和无关文件。
- 用源码核对实际方法和参数。区分「已核对源码」「项目文档声明」「建议／待验证」「已运行验证」。只有确实执行了检查才写明运行结果。没有看到模型文件、运行配置或测试时，写出缺的证据和核查办法。

## 在同一张白板按需展开

- 总览回答项目为谁解决什么问题。功能卡按用户可辨认的能力划分，一张卡说清用途和边界。子卡再讲调用路径、方法或参数、变更位置，或者独立的约束与验证项。根据当前问题挑合适的维度。
- 每张卡只回答一个能单独说清的问题。标题点出对象和动作，正文用一到三句说明行为、条件或证据；能核对时附仓库相对路径和符号。父卡概括共同能力，细节放进自己所属的子卡。同级卡分工清楚，别把同一解释复制几遍。
- 需求正文、精确规格、输入样例、接口与张量表、对比数据和详细验证步骤适合单独的附件或仓库文档。一份材料绑定具体需求卡，正文保留结论、附件入口和用途。只链接已经存在或本次有权生成且实际写出的材料；待补材料标为待补。验收保留输入、触发动作、可观察结果和可用证据。
- 固定卡适合放用户确认的关键需求、不可破坏的约束和已确认决定。图钉表示优先考虑；卡上的结论是否可靠仍取决于证据。意见冲突时指出冲突，保留用户的原有决定并说明需要核对的地方。

## 用卡片下方的「+」继续问

提交一句你想看清的问题。沿当前卡的上下级路径理解它在项目中的作用，对照直接子卡，找出本轮缺失的解释。围绕当前问法补一层 2–6 张短卡；遇到另一张已经讲清的卡，可在正文中引用它。需要更深的细节时继续在对应子卡上追问。

随每张新卡给出一个可直接确认的后续问题。用这张卡自己的主题和已有证据，挑一个正文还没答清的具体条件、实现机制或验收点。旧卡缺推荐时，先根据当前卡和已有下级判断一个问题，等用户确认后再展开。保留用户主动输入的内容。

例如选中 E12「检测与分类｜先找区域，再判候选」，输入「展开说明 ONNX 检测怎么预处理、怎样从框裁剪，分类如何定尺寸」。可依源码把这一层做成：

1. **检测输入｜缩放还是补边**：说明检测入口的尺寸来源，如何变换图像、维护比例或偏移；核实是否用了 letterbox。
2. **检测输出｜候选框还原**：说明怎样从模型结果取得候选框，如何映射回原图，以及有证据的过滤行为。
3. **分类前｜从原图裁剪区域**：说明裁剪依据、坐标边界、无候选时的行为；把确认过的条件写清楚。
4. **分类输入｜尺寸与归一化**：说明 resize 的尺寸来源、通道或归一化方法，交代不同模型的实质差异。
5. **怎么验｜用样例比对坐标与分类**：列出能验证非正方形图片、边缘框等行为的样例和可观察结果。没有真实结果时标为待测。

这些是可核实的问题方向。实际卡片引用读过的源文件和符号，具体尺寸、算法和检测效果以本轮证据为准。若继续问「边缘框会不会越界」，在裁剪卡下开下一层。

## 模型收到什么

- 白板发出用户这句话、焦点卡及其祖先路径、已存在的直接子卡，以及相关或全局的固定卡摘要和可见关联。把路径用作作用范围，已有子卡用来避免重复，固定卡用于明确约束。附件或源码证据按本次请求能力提供。
- 配置 API Key 只连接模型。API 轮次从白板发送的材料理解项目：源码读取取决于当前请求有没有提供受限读取工具；仅在文本里出现路径时，视为定位线索。没有读到材料时直说未核实。Codex／ZCode 也遵循本轮提供的路径、读取范围及权限。
- 「+」请求只返回当前卡下的短卡内容。白板负责校验结果、分配 ID、把新卡挂到当前卡以及布局和保存。模型无需决定现有卡的父子关系，也不应改源码、移动别处卡片或覆盖图钉。要验证实现或修改代码，按独立请求的授权执行。
