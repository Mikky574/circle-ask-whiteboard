# 圈问白板：从使用需求读懂代码仓

## 从一个实际场景出发

- 先弄清使用者要完成什么、输入和输出是什么、什么情况算失败。接手项目的读者还需要知道从哪里开始读、变更在哪一层、哪些约束不能破坏、如何得到可复现的验收结果。
- 在项目授权的目录内找 README、仓库说明和构建清单，再跟一条真实调用路径：用户动作 → 入口 → 核心方法与配置 → 返回值、错误或回退 → 可核对的测试。首轮用少量有代表性的源码、配置和测试建立能力地图。证据够分类即可落板，具体参数和异常路径等细节在对应章节下钻时补齐。跳过凭据、生成物和无关文件。
- 用源码核对实际方法和参数。区分「已核对源码」「项目文档声明」「建议／待验证」「已运行验证」。只有确实执行了检查才写明运行结果。没有看到模型文件、运行配置或测试时，写出缺的证据和核查办法。

## 在同一张白板按需展开

1. 先从入口与可见结果整理真实使用路径，再按独立的用户目标归纳功能，最后生成树形提纲。总览用一两句交代谁使用、输入是什么、得到什么结果和项目边界。功能数量由证据决定，简单项目可以只有一项；不按目录数或剩余卡号补齐。按动作与结果命名，例如「不确定时保留待复核结果」。领域名词可以保留，但类名换成中文不能替代功能提炼。
2. 总览和一级功能脱离下级也应独立可读：说明用途、输入输出、边界与怎样核对。下一层按真实使用场景展开，交代何时触发、用户做什么、看到什么结果及重要失败情况。不要把整个功能、通用技术层和某个参数放成同级。场景不足时保持浅分支，避免只有一个重复子卡的包装层。
3. 文件、调用、参数与源码测试细节归到对应场景的实现依据，按需展开。`repositoryFiles` 放相对文件路径，外层正文不强制写文件名。原生初始化会检查文件是否可读，并把源码片段留到更深一层。通过服务技能交付时遵守其单次层宽约束。
4. 只看总览及一级标题与结果，读者应能说清项目有哪些不同的用途。再检查一条场景能否追到实现依据与核对办法；缺证据的结论标为待核实。别用「状态管理」「工具函数」「配置」等内部分类替代项目功能，除非它们确实是本产品提供给使用者的独立能力。

原生初始化的功能记录为 `capability: {version:1, audience, input, outcome, boundary, verification}`，五项说明各不超过 200 字。总览和一级功能必须提供，深层可省略。`verification` 说明怎样核对及是否实际验证；存在文件不等于已经运行。卡片被改写时应同步修订这份记录，未同步的旧记录会清除，避免它遮住新正文。

- 需求正文、精确规格、输入样例、接口与张量表、对比数据和详细验证步骤适合单独的附件或仓库文档。一份材料绑定具体需求卡，正文保留结论、附件入口和用途。只链接已经存在或本次有权生成且实际写出的材料；待补材料标为待补。验收保留输入、触发动作、可观察结果和可用证据。
- 固定卡适合放用户确认的关键需求、不可破坏的约束和已确认决定。图钉表示优先考虑；卡上的结论是否可靠仍取决于证据。意见冲突时指出冲突，保留用户的原有决定并说明需要核对的地方。

## 用卡片下方的「+」继续问

按问题提出一层短卡，通常只需 1–3 个能独立回答问题的同粒度主题。必须合起来才能解释的材料写在同一张卡。项目画布先显示候选，用户勾选后加入。用户填写了方向时，围绕该方向展开；留空时，沿当前卡的功能和既有下级挑一个有依据的条件、场景或验收点。遇到已有答案可引用，细节可从对应子卡继续展开。

使用「补充项目功能」时，从项目提供的入口和可复用结果归纳能力。一次业务操作和特定输入走同一条功能路径，留在使用场景层。可以切到「补充使用场景」或「补充实现与验证」。检查已有子卡与邻近主题的重合度，找不到独立的新内容时允许空结果。

例如选中 E12「检测与分类｜先找区域，再判候选」，输入「展开说明 ONNX 检测怎么预处理、怎样从框裁剪，分类如何定尺寸」。可依源码把这一层做成：

1. **检测如何找区域**。再展开「输入尺寸和 letterbox」「候选框还原」「置信度过滤」。
2. **分类如何判候选**。再展开「从原图裁剪」「分类 resize 和归一化」「无候选时的处理」。
3. **怎么验证端到端结果**。再展开「长宽比样例」「边缘框样例」「模型结果对比」，每项写出可观察的结果。

这些是可核实的问题方向。实际卡片引用读过的源文件和符号，具体尺寸、算法和检测效果以本轮证据为准。若继续问「边缘框会不会越界」，在裁剪卡下开下一层。

## 模型收到什么

- 确认时，白板发出用户填写的方向、焦点卡及其祖先路径、已存在的直接子卡，以及相关或全局的固定卡摘要和可见关联。把路径用作作用范围，已有子卡用来避免重复，固定卡用于明确约束。附件或源码证据按本次请求能力提供。
- 配置 API Key 只连接模型。API 轮次从白板发送的材料理解项目：源码读取取决于当前请求有没有提供受限读取工具；仅在文本里出现路径时，视为定位线索。没有读到材料时直说未核实。Codex／ZCode 也遵循本轮提供的路径、读取范围及权限。
- 「+」请求只返回当前卡下的短卡内容。白板负责校验结果、分配 ID、把新卡挂到当前卡以及布局和保存。模型无需决定现有卡的父子关系，也不应改源码、移动别处卡片或覆盖图钉。要验证实现或修改代码，按独立请求的授权执行。
